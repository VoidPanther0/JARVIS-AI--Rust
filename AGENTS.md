# JARVIS AI - Universal AI Agent Instructions

## 1. Project Identity

Project: JARVIS AI  
Repository: VoidPanther0/JARVIS-AI--Rust  
Version: 0.1.0-alpha.1  
License: MIT  
Primary Language: Rust  
Project Type: Open-source personal AI assistant.

JARVIS is a modular, cross-platform personal AI assistant designed for desktop and mobile devices.

The goal is to build a reliable assistant with AI conversations, voice interaction, memory, and permission-controlled device automation.

This project must prioritize stability, security, performance, modularity, and maintainability.

## 2. Development Priorities

Platform development order:

1. Windows 10/11 x64.
2. Linux desktop.
3. Android.
4. macOS.
5. iOS.

Do not sacrifice cross-platform architecture to implement Windows-only features.

Keep shared business logic independent from platform-specific functionality.

The developer currently uses Windows 11, 16GB RAM, and CPU-only hardware. Keep development and runtime resource requirements reasonable.

## 3. Technology Stack

Core:
- Rust stable.
- Cargo workspace.
- Tokio for asynchronous operations.
- SQLite for persistent local data.
- SQLx for database access.

Desktop:
- Tauri 2.
- HTML, CSS, JavaScript.

Future voice:
- Whisper-compatible speech recognition.
- Piper-compatible speech synthesis.
- Pluggable wake-word detection.

Build and distribution:
- GitHub Actions.
- Windows x64.
- NSIS installer.
- MSI installer.

Do not introduce unnecessary frameworks or dependencies.

## 4. Repository Architecture

Preserve the established structure:

apps/
  desktop/
    src-tauri/
    ui/

crates/
  jarvis-core/
  jarvis-ai/
  jarvis-voice/
  jarvis-memory/
  jarvis-platform/

docs/
.github/
  workflows/

Responsibilities:

### jarvis-core
Application configuration, shared types, errors, logging, permissions and common services.

### jarvis-ai
AI provider interfaces, provider registry, request handling and response abstraction.

### jarvis-voice
Speech recognition, speech synthesis and wake-word abstractions.

### jarvis-memory
SQLite storage, migrations, conversation history and memory management.

### jarvis-platform
Operating-system integrations, system information and permission-checked device operations.

### apps/desktop
Tauri application, frontend, application lifecycle and desktop integration.

Do not move responsibilities between crates without a clear architectural reason.

## 5. Mandatory Coding Rules

- Follow Rust idioms and ownership principles.
- Prefer clear, maintainable code over clever abstractions.
- Use explicit error handling.
- Avoid unnecessary unwrap() and expect() in production paths.
- Avoid blocking operations in asynchronous runtime tasks.
- Use structured logging.
- Keep modules focused.
- Document public APIs.
- Avoid duplicated business logic.
- Keep dependencies minimal.
- Never silently ignore errors.
- Do not introduce breaking API changes without documenting them.

## 6. Security Rules

Security is mandatory.

- Never hardcode API keys, passwords or tokens.
- Never commit .env files containing secrets.
- Validate external input.
- Treat AI-generated output as untrusted input.
- Never execute arbitrary shell commands generated by an AI model.
- Never allow unrestricted filesystem access.
- Require explicit user approval for sensitive operations.
- Use least-privilege permissions.
- Protect stored credentials.
- Do not log sensitive user information.
- Never disable security controls to make tests pass.

All device automation must go through a controlled permission layer.

## 7. AI Agent Rules

Before changing code:

1. Inspect the existing implementation.
2. Read this AGENTS.md.
3. Read relevant documentation.
4. Identify affected crates and dependencies.
5. Explain the planned changes.
6. Preserve working functionality.

During development:

- Make focused changes.
- Do not rewrite unrelated modules.
- Do not invent completed features.
- Do not create fake implementations.
- Do not add unnecessary placeholder modules.
- Do not change public APIs without justification.
- Update documentation when architecture changes.

After development:

1. Run formatting checks.
2. Run Clippy.
3. Run relevant tests.
4. Build affected targets where available.
5. Fix regressions.
6. Report exactly what passed and failed.

Never claim a test passed unless it was actually executed.

## 8. Dependency Management

Before adding a dependency:

- Check whether existing dependencies already solve the problem.
- Review maintenance and security status.
- Consider compile time and binary size.
- Check cross-platform compatibility.
- Avoid duplicate libraries.

Keep Cargo.lock committed for application builds.

Do not upgrade all dependencies without a reason.

## 9. Cross-Platform Rules

Keep shared Rust logic platform-independent.

Use platform-specific modules or adapters for:

- Windows APIs.
- Linux integrations.
- Android integrations.
- macOS integrations.
- iOS integrations.

Use compile-time platform conditions only where necessary.

Never assume a desktop filesystem, microphone API or process-control interface exists on mobile.

## 10. Performance Rules

- Optimize for CPU-only hardware.
- Avoid unnecessary background processes.
- Avoid excessive memory allocations.
- Use asynchronous I/O where appropriate.
- Keep startup time reasonable.
- Avoid loading large AI models automatically.
- Make local AI models optional.
- Avoid GPU-only requirements.

## 11. Git Rules

Use clear commit messages:

feat: add AI provider interface
fix: correct database initialization
refactor: separate platform adapters
docs: update architecture documentation
test: add memory storage tests
build: improve Windows release workflow
security: restrict command execution

Never commit:

- API keys.
- Local database files.
- Build output.
- Temporary files.
- Personal configuration.
- User data.

Do not force-push or rewrite shared Git history without explicit authorization.

## 12. Versioning

Follow Semantic Versioning.

Development releases:
0.x.y-alpha.n
0.x.y-beta.n

Stable releases:
1.0.0
1.0.1
1.1.0
2.0.0

Never claim a release is stable without the required tests and release verification.

## 13. GitHub Actions

All workflows must:

- Use pinned or controlled action versions.
- Use minimum required permissions.
- Run formatting and lint checks.
- Run tests.
- Build only supported targets.
- Protect release credentials.
- Verify generated installers.
- Upload artifacts only after successful builds.

Never publish a release from an unverified build.

## 14. Documentation

Update relevant documentation whenever you change:

- Architecture.
- Public APIs.
- Dependencies.
- Build configuration.
- Installation.
- Security behavior.
- Supported platforms.
- Release procedures.

Keep README.md honest about implemented versus planned features.

## 15. Definition of Done

A task is complete only when:

- Implementation exists.
- Relevant tests pass.
- Formatting passes.
- Clippy passes where applicable.
- Build succeeds for the affected target.
- Security implications are reviewed.
- Documentation is updated.
- Limitations are reported.

## 16. Final Agent Report

After every development task, provide:

1. Summary of changes.
2. Files created.
3. Files modified.
4. Dependencies added or removed.
5. Tests executed.
6. Build results.
7. Known issues.
8. Remaining work.

Do not hide failures.

## Final Instruction

Build JARVIS as a real, maintainable open-source product.

Preserve the architecture, protect user data, prioritize stability, and never pretend incomplete functionality is finished.
